# 리뷰 목록의 PR을 Concord 작업으로 맡기기

TL;DR

- 오른쪽 패널의 세 리뷰 목록(리뷰 요청, 받은 리뷰, 보낸 리뷰), 뇌 그래프의 줄기, 칸반의 '맡긴 일' 칸은 모두 같은 확인 창을 거쳐 PR 하나를 맡깁니다.
- 다른 사람의 PR은 `concord:review-until-approve`, 내 PR은 그 PR 하나로 범위를 정한 `concord:pr-to-merge`를 실행합니다.
- 실행하는 머신은 PR 저장소의 로컬 클론에서 mien 프로필과 GitHub 계정을 확인하고, 계정과 PR 작성자가 작업 종류와 맞을 때만 tmux 안의 Claude Code 세션을 시작합니다.
- 확인 창에는 그 머신이 확인한 저장소, PR, 작업, 실행 계정, 허용 동작을 보여 주고, 시작할 때 같은 확인을 다시 해 결과가 달라졌으면 시작하지 않습니다.
- thync가 직접 리뷰를 받아 올리던 1회성 리뷰어(`thync/review.py`)와 `reflex_skills` 설정은 없앱니다.

## 목표

- 세 리뷰 목록의 항목을 줄기에 끌어 놓거나, 항목의 '맡기기' 버튼(키보드로 누를 수 있음)으로 맡깁니다.
- 받은 리뷰 항목은 리뷰가 아니라 그 리뷰가 달린 내 PR을 맡깁니다. 같은 PR에 리뷰어가 여럿이어도 대상은 PR 하나입니다.
- 어느 진입점에서 맡겨도 같은 PR 노드는 같은 작업과 같은 대상을 고릅니다.
- 준비물이 없으면(기능 꺼짐, `claude`·`tmux`·`gh` 없음, Concord 스킬 없음, 클론 없음, 계정 확인 실패) 확인 창이 이유를 보여 주고, 아무 작업도 시작하지 않으며 '맡긴 일' 기록도 남기지 않습니다.

## 하지 않는 것

- 저장소 전체를 대상으로 하는 병합 감시. `pr-to-merge`에는 항상 `OWNER/REPO#N` 하나만 넘깁니다.
- 리뷰·병합 규칙의 재구현. 승인 조건, 병합 조건, 신뢰 선언, 대기 방식은 Concord 스킬이 정합니다.
- Codex 하네스에서의 실행. thync는 `claude`만 실행하므로 Concord의 Claude Code 동작(백그라운드 감시)을 따릅니다.

## 작업 고르기

| 노드의 역할 | 확인할 작성자 | 실행하는 스킬 | 스킬에 넘기는 범위 | 확인 창의 허용 동작 |
| --- | --- | --- | --- | --- |
| `review` (리뷰 요청) | 실행 계정이 아닌 사람 | `concord:review-until-approve` | PR 주소 하나 | 리뷰 게시, 깨끗한 라운드의 승인 |
| `sent` (보낸 리뷰, 받은 리뷰) | 실행 계정 | `concord:pr-to-merge` | `OWNER/REPO#N` 하나, 병합 허락도 이 PR 하나 | 리뷰 지적 수정, 커밋·push, 답글, 자동 리뷰어 스레드 resolve, 리뷰 재요청, PR 본문 수정, 뒤처진 브랜치 갱신, 조건을 채운 경우 병합, 병합 뒤 실패한 작업 재실행과 티켓 상태 변경·댓글 |

- 역할은 화면이 보낸 노드에서 읽고, 작성자는 실행하는 머신이 `gh api repos/<저장소>/pulls/<번호>`로 다시 읽습니다. 역할과 작성자가 맞지 않으면(내 PR이 리뷰 요청 목록에 있거나, 다른 계정으로 로그인해 내 PR이 남의 PR이 된 경우) 시작하지 않습니다.
- 닫히거나 병합된 PR도 시작하지 않습니다.
- 초안인 내 PR은 시작하지 않습니다. `pr-to-merge` 스크립트는 초안을 아무 보고 없이 건너뛰므로, 세션이 아무것도 하지 않고 대기 상태로 남습니다.

## 실행 계정

- 실행하는 머신은 `company_roots` 바로 아래 폴더(이름순), 그다음 알려진 세션 폴더 순서로 보고, `origin`이 PR 저장소인 첫 클론을 씁니다. 확인 창에 그 폴더를 보여 줍니다. 클론이 없으면 시작하지 않습니다. 계정을 정할 기준이 없고, `pr-to-merge`는 클론에서 고칩니다.
- `mien`이 있으면 클론에서 `mien which`로 프로필을 읽습니다. 프로필이 없으면 시작하지 않습니다. 프로필이 있으면 계정 확인(`gh api user`)과 Claude Code 프로세스 전체를 `mien exec <프로필>`로 실행하고, 스킬에도 그 프로필을 알립니다. 서버 프로세스의 기본 `gh` 계정은 쓰지 않습니다.
- `mien`이 없는 머신에서는 서버 프로세스의 `gh` 계정이 실행 계정입니다. 확인 창에 "프로필 없음"으로 보여 주고, 작성자 확인은 같은 방식으로 합니다.

## 확인과 시작

1. 화면이 `POST /reflex {id, check: true}`를 보냅니다. 실행하는 머신이 위의 확인을 모두 하고, 통과하면 `plan`(저장소, 번호, 주소, 스킬, 프로필, 계정, 작성자, 클론 경로)을 돌려줍니다. 이 단계는 아무것도 시작하거나 저장하지 않습니다.
2. 확인 창은 `plan`과 허용 동작을 보여 줍니다. 취소하면 요청을 더 보내지 않습니다.
3. 시작을 누르면 화면이 `POST /reflex {id, plan}`을 보냅니다. 실행하는 머신은 확인을 처음부터 다시 하고, 스킬·계정·프로필이 화면이 보여 준 `plan`과 다르면 `409`로 거절합니다.
4. 통과하면 tmux 세션 `thync-<소유자>-<저장소>-<번호>`를 클론 폴더에서 만들고, 그 안에서 Claude Code를 `--permission-mode auto`로 실행합니다. `~/.thync`, `~/.ssh`, `~/.claude/settings.json`은 Read 도구에서 거부합니다. 셸 명령으로 읽는 것은 막지 않습니다. 첫 프롬프트는 `/<스킬> <PR 주소>`와 범위·계정을 적은 지시이고, `pr-to-merge`에는 병합 허락을 덧붙입니다. 신뢰·보증 문구는 넣지 않습니다.

같은 PR의 세션 이름은 하나뿐이고 `tmux new-session`이 같은 이름을 거절하므로, 받은 리뷰 여러 줄이나 보낸 리뷰 줄에서 같은 PR을 거듭 맡겨도 세션은 하나만 돕니다.

## 다른 서버에서 실행하기

`reflex_host`가 있으면 허브는 확인과 시작 두 요청 모두 PR 노드를 그대로 그 서버에 한 번 넘기고(`X-Thync-Forwarded: 1`), 받은 답을 화면에 전합니다. 프로필과 계정은 그 서버의 클론에서 정합니다. 그 서버에 연결되지 않으면 허브는 `503`을 돌려주고 자기 머신에서 대신 실행하지 않습니다. 넘겨받은 서버는 다시 넘기지 않으며, 그 서버에도 `reflex_host`가 있으면 `503`으로 거절합니다.

## 진행 상태

실행기는 tmux 안의 대화형 Claude Code 세션입니다. Concord의 두 스킬은 이 세션 안에서 백그라운드 명령으로 기다리고, 기다리는 동안 Claude의 차례는 끝나 있습니다. 그래서 thync는 세션이 감시 중인지 사용자의 답을 기다리는지 구분하지 않고, 아는 것만 보여 줍니다.

| tmux 세션 | 세션 기록 | 종료 코드 파일 | 카드에 보이는 상태 |
| --- | --- | --- | --- |
| 있음 | 아직 없음 | - | 시작함 |
| 있음 | Claude가 일하는 중 | - | 작업 중 |
| 있음 | 선택 질문을 기다림 | - | 답을 기다림 |
| 있음 | Claude의 차례가 끝남 | - | 대기 중: 백그라운드 감시 중이거나 입력을 기다림. 접속 명령을 함께 보여 줍니다 |
| 없음 | - | `0` | 끝남 |
| 없음 | - | `0`이 아님 | 실패 (종료 코드) |
| 없음 | - | 없음 | 끝남 (종료 코드 모름) |

종료 코드 파일은 `THYNC_HOME/handoff/<세션 이름>.exit`입니다. tmux가 실행하는 명령이 끝날 때 셸이 종료 코드를 쓰고, 새로 시작할 때 지웁니다.

`review-until-approve`는 Claude Code에서 Claude 리뷰어를 쓰려면 사용자가 그 대화에서 직접 신뢰를 선언해야 합니다. thync는 이 선언을 대신 쓰지 않습니다. 세션이 선언을 요구하면 '대기 중'이 되고, 사용자는 접속 명령으로 세션에 들어가 답합니다. 세션이 선택 질문으로 물으면 '답을 기다림'이 되고, thync 화면의 선택 대기 창에서 답해도 됩니다. 둘 다 사용자 본인의 입력입니다.

대화형 세션은 작업이 끝나도(승인, 병합, 닫힘) 스스로 종료하지 않습니다. 사용자가 세션을 끝낼 때까지 카드는 '대기 중'이고, 같은 PR을 다시 맡기면 `409`입니다.

## Stateful changes

상태는 `THYNC_HOME/reflex.json`의 PR별 기록, tmux 세션, 종료 코드 파일입니다. Concord의 원장과 상태 파일은 Concord가 관리합니다.

| State | Event | Outcome | Kind | Evidence |
|---|---|---|---|---|
| 기록 없음 | 확인 요청 | `plan` 반환. tmux·기록·종료 코드 파일 변화 없음 | introduced | |
| 기록 없음 | 시작, 확인 통과 | tmux 세션 1개, 기록 저장(스킬·프로필·계정·클론·시작 시각), 종료 코드 파일 없음 | changed | |
| 기록 없음 | 시작, 준비물 없음·작성자 불일치·PR 닫힘·초안인 내 PR | 4xx/5xx와 이유. tmux·기록 변화 없음 | introduced | |
| 기록 없음 | 시작, 화면의 `plan`과 계정·프로필·스킬이 다름 | `409`. tmux·기록 변화 없음 | introduced | |
| 세션 돌고 있음 | 같은 PR을 다시 시작(받은 리뷰 다른 줄 포함) | `409`와 접속 명령. 기록과 세션 그대로 | changed | |
| 세션 끝남 | 같은 PR을 다시 시작 | 이전 종료 코드 파일 삭제, 새 세션, 기록 교체 | changed | |
| 기록 없음 | `tmux new-session` 실패 | `500`. 기록 없음 | unchanged | |
| 세션 돌고 있음 | Claude Code가 종료 | 종료 코드 파일 기록. 카드가 끝남 또는 실패로 바뀜 | introduced | |
| 1회성 리뷰 기록(`tmux` 키 없음) | 화면 갱신 | 카드로 보이지 않음. 파일은 그대로 | introduced | |
| 허브 | 확인 또는 시작, `reflex_host` 연결됨 | 그 서버로 한 번 넘김. 허브에서는 실행·저장 없음 | changed | |
| 허브 | 확인 또는 시작, `reflex_host` 연결 안 됨 | `503`. 허브에서 실행·저장 없음 | unchanged | |
| 넘겨받은 서버 | 넘겨받은 요청, 자신에게도 `reflex_host` 있음 | `503`. 다시 넘기지 않음 | unchanged | |

서버 재시작은 기록과 tmux 세션을 바꾸지 않습니다. 카드는 재시작 뒤에도 tmux와 종료 코드 파일로 상태를 다시 계산합니다.

## 비용과 남는 위험

- 다른 사람의 PR 리뷰가 읽기 전용 1회성 실행에서 auto 권한의 대화형 세션으로 바뀝니다. Read 도구 거부 목록은 셸 읽기를 막지 않습니다. Concord는 리뷰어를 PR 헤드의 임시 클론에서 실행하지만, 세션 자체는 사용자의 클론에서 auto 권한으로 돕니다. PR 본문과 코드는 외부 입력이며, Claude 리뷰어는 사용자의 신뢰 선언 없이는 실행되지 않습니다.
- 내 PR은 확인 창에서 시작을 누르는 것으로 그 PR 하나의 병합을 허락합니다. 병합 조건 판단은 `pr-to-merge` 스크립트가 합니다.
- 클론이 둘 이상이면 찾는 순서에서 먼저 나온 클론의 프로필이 실행 계정이 됩니다. 확인 창이 폴더와 계정을 보여 주므로 시작 전에 알 수 있습니다.
- 리뷰 요청이 온 저장소의 클론이 없으면 맡길 수 없습니다. 이전 1회성 리뷰어는 클론 없이 동작했습니다.
- '대기 중'은 감시 중과 입력 대기를 구분하지 않습니다. 구분하려면 세션 기록에서 백그라운드 명령 상태를 읽어야 하는데, 세션 기록 형식은 공개된 형식이 아닙니다.

## 고려했지만 택하지 않은 것

- **`claude -p`로 실행**: 한 번의 응답으로 끝나므로 두 스킬의 백그라운드 감시가 함께 끝납니다.
- **서버 프로세스의 기본 `gh` 계정 사용**: 여러 계정을 쓰는 머신에서 리뷰나 병합이 다른 계정으로 올라갈 수 있습니다.
- **확인 없이 바로 시작**: 확인 창이 실행 계정을 보여 줄 수 없습니다.
- **`reflex_skills`로 스킬 이름 바꾸기**: 첫 프롬프트의 범위·병합 허락 문구가 두 스킬의 인자 형식에 맞춰져 있어 다른 스킬과 바꿔 쓸 수 없습니다.
