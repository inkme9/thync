# Obsidian vault 출처

이슈: [#2](https://github.com/inkme9/thync/issues/2)

## 결정

`thync/sources/obsidian.py`가 설정한 vault 폴더를 직접 읽습니다. Obsidian 앱이나 플러그인을 거치지 않습니다. 수집 구간 안에 수정된 `.md` 파일마다 노트 하나를 돌려주고, `graph.build_graph()`가 이를 노드와 연결로 넣습니다.

### 설정

```json
{
  "sources": ["claude_code", "codex", "github", "jira", "notion", "obsidian"],
  "obsidian_vaults": [{"path": "~/vault", "profile": "회사", "name": "work"}]
}
```

- `sources`의 기본값에 `obsidian`을 넣습니다. `obsidian_vaults`가 비어 있으면 아무것도 읽지 않으므로, 기존 설정 파일은 고치지 않아도 지금과 같이 동작합니다.
- `profile`은 `회사` 또는 `개인`입니다. 생략하거나 다른 값을 쓰면 `개인`입니다.
- `name`은 thync 안에서 vault를 구분하는 이름이고, 생략하면 `path`의 마지막 폴더 이름입니다. 노드 id에만 씁니다. Obsidian에 등록된 vault 이름과 같을 필요가 없습니다.
- 이름이 비었거나 `:`이 들어 있으면 건너뛰고 경고합니다. 이름은 노드 id `obsidian:<이름>:<경로>`의 한 칸이기 때문입니다.
- 이름이 앞의 vault와 겹치는 항목은 건너뛰고 서버 로그에 한 번 경고합니다. 폴더 이름이 같은 vault 두 개를 함께 쓰려면 `name`을 다르게 적습니다.
- `path`는 절대 경로나 `~`로 시작하는 경로여야 합니다. 상대 경로는 thync를 실행한 위치에 따라 달라지고 노트 주소도 틀어지므로, 건너뛰고 서버 로그에 경고합니다.
- `path`가 폴더가 아니거나 읽을 수 없으면 그 vault는 건너뜁니다.

### 읽는 범위

- vault 아래의 `.md` 파일 가운데 파일 수정 시각이 최근 30일(`MAX_DAYS`) 안인 것을 찾습니다. 화면에서 고른 기간으로는 `build_graph()`가 다시 거릅니다.
- 이름이 `.`으로 시작하는 폴더(`.obsidian`, `.trash` 등)와 칸반 카드 폴더(`CARDS_DIR`)는 들어가지 않습니다. 카드 폴더를 vault 안에 두면 카드 파일이 노트로 한 번 더 보이기 때문입니다.
- 심볼릭 링크는 따라가지 않고, 링크인 파일도 읽지 않습니다. vault 밖의 파일이 읽히지 않게 하기 위해서입니다. 목록을 만든 뒤 파일이 링크로 바뀌는 경우에 대비해 파일을 열 때도 링크를 따라가지 않습니다(`O_NOFOLLOW`). 이 장치는 파일 자신만 막습니다. 목록을 만든 뒤 상위 폴더가 링크로 바뀌는 경우는 막지 못합니다.
- 수정 시각이 최근인 순서로, 설정한 vault 전체를 합쳐 최대 100개까지만 씁니다.
- 파일의 수정 시각이 지금보다 뒤이면 지금 고친 것으로 봅니다. 시계가 틀리거나 동기화 도구가 미래 시각을 남긴 경우입니다.
- 파일마다 앞쪽 256KB까지만 읽습니다. 그보다 큰 파일은 잘린 곳에서 낱말이 끊길 수 있으므로(`ABC-123`이 `ABC-12`로), 마지막 공백 뒤의 조각은 버립니다. 노트 링크는 닫는 `]]`가 있을 때만 인정하므로, 이름에 공백이 있는 링크가 잘려도 더 짧은 이름의 다른 노트로 연결되지 않습니다. 잘린 곳에서 코드 블록이 닫히지 않았으면 그 블록이 시작한 곳부터 끝까지를 코드로 보고 지웁니다.

### 훑는 시점

- 서버(`thync/server.py`)는 Notion 출처처럼 배경 스레드(`refresh_forever`)를 시작해 vault를 훑고 결과를 보관합니다. 한 번 훑기를 마치면 30초 쉬고 다시 훑습니다.
- 배경 스레드를 시작한 프로세스에서는 `build_graph()`가 보관된 결과만 읽고, 직접 훑지 않습니다. 보관된 결과가 얼마나 오래되었는지는 따지지 않습니다. 그래서 `GET /graph.json` 요청은 vault 크기 때문에 느려지지 않고, 서버를 켠 뒤 첫 훑기가 끝날 때까지는 노트가 보이지 않습니다.
- 배경 스레드를 시작하지 않은 프로세스(MCP 서버 `thync/mcp.py`, 테스트)에서는 보관된 결과가 30초보다 오래되었을 때 호출한 쪽에서 직접 훑습니다. 이 경우 호출은 훑기가 끝날 때까지 기다립니다.
- 스레드를 시작했는지는 서버가 부르는 `obsidian.start()`가 스레드를 띄우기 전에 모듈에 남기는 표시로 구분합니다.

### 본문에서 뽑는 것

본문 문장은 저장하지 않고, 아래 네 가지만 뽑아 남깁니다. 코드 블록(```` ``` ````으로 감싼 부분)과 인라인 코드는 먼저 지우고 찾습니다.

| 대상 | 인식하는 형태 | 그래프에 넣는 방식 |
| --- | --- | --- |
| 노트 링크 | `[[노트]]`, `[[폴더/노트]]`, `[[노트\|표시 이름]]`, `[[노트#제목]]`, `![[노트]]` | 같은 vault에서 파일 이름이 같은 노트가 그래프에 있으면 두 노트를 연결합니다. 대소문자는 구분하지 않고, 유니코드 정규화(NFC)를 한 뒤 비교합니다. macOS가 한글 파일 이름을 자모로 풀어(NFD) 저장하는 경우가 있기 때문입니다. 표 안에서 쓰는 `[[노트\\|표시 이름]]`도 `노트`를 가리킵니다 |
| 태그 | 본문의 `#태그`, 머리말(frontmatter)의 `tags:` | 같은 vault의 그래프에 있는 노트 두 개 이상이 같은 태그를 가지면 태그 노드 하나를 만들어 그 노트들과 연결합니다. 대소문자는 구분하지 않습니다 |
| Jira 키 | 제목(확장자를 뺀 파일 이름)과 본문의 `ABC-123` | 접두어가 브랜치 이름이나 배정 티켓에서 확인된 경우에만 키로 봅니다(기존 규칙). 티켓과 연결합니다. 제목에 키가 있으면 첫 키의 작업 단위에 노트를 넣습니다. 본문의 키는 연결만 하고 노트의 작업 단위를 바꾸지 않습니다 |
| PR 주소 | `https://github.com/<소유자>/<저장소>/pull/<번호>` | `pr:<주소>` 노드와 연결합니다. 그 PR 노드가 없으면 만듭니다. 주소의 대소문자가 GitHub이 주는 주소와 다르면 같은 PR로 보지 못하고 노드를 따로 만듭니다 |

- 노트 하나에서 Jira 키와 PR 주소는 각각 앞에서부터 10개까지만 씁니다. 목록 노트 하나가 그래프를 덮지 않게 하기 위해서입니다.
- 본문의 `#`은 줄의 처음이나 공백 바로 뒤에 있을 때만 태그의 시작으로 봅니다. `https://example.com/#top`의 `#top`은 태그가 아닙니다. `#123`이나 `#2026-11`처럼 글자가 하나도 없는 것과, `#` 뒤에 공백이 오는 제목 줄(`# 제목`)도 태그가 아닙니다.

### 제목과 본문

- 노트의 제목은 확장자를 뺀 파일 이름입니다. 본문 첫 줄의 제목(`# ...`)이나 머리말의 `title:`은 제목이 아니고 본문입니다.

### 본문의 Jira 키와 Jira 조회

티켓 노드를 만들면 thync는 그 키를 Jira Cloud에 조회합니다(`jira.py`의 `_seen`, `refresh_forever`).

- 본문의 키도 제목의 키와 똑같이 티켓 노드로 만들고 조회합니다. 내가 맡지 않은 동료의 티켓이 노트에 적혀 있어도 연결하기 위해서입니다. 따라서 본문에 적힌 티켓 번호는 설정한 Jira 서버로 나갑니다. Jira 토큰을 설정하지 않았으면 조회하지 않습니다.
- 노트에서 나온 키만 따로 세는 제한은 두지 않습니다. 줄이는 장치는 위의 두 가지입니다: 접두어가 확인된 키만 쓰고, 노트 하나에서 10개까지만 씁니다.
- 조회 대상(`_seen`)은 프로세스마다 100개(`MAX_KEYS`)까지 먼저 온 순서로 채워지고 비워지지 않습니다. 노트의 키도 그래프가 다루는 다른 모든 Jira 키(세션, 커밋, 리뷰 요청 제목, 내가 올린 PR 제목, 배정 티켓, Notion 제목)와 이 100개를 함께 씁니다. 이 한계는 "치르는 비용"에 적습니다.

### 노드

| 노드 | id | 종류(`kind`) | `kind_label` | 프로필 |
| --- | --- | --- | --- | --- |
| 노트 | `obsidian:<vault 이름>:<vault 기준 경로>` | `dailyNote` | Obsidian 노트 | vault의 프로필 |
| 태그 | `obsidian-tag:<vault 이름>:<태그>` | `concept` | Obsidian 태그 | vault의 프로필 |
| 노트가 만든 PR | `pr:<주소>` | `source` | PR | 그 PR을 처음 만든 노트의 vault 프로필 |
| 노트가 만든 Jira 티켓 | `jira:<키>` | `project` | Jira 티켓 | 회사 |

- 태그 노드의 `concept`은 brain-atlas에 이미 있는 종류(`vendor/brain-atlas/src/types.ts`)이지만 thync가 쓰는 것은 처음입니다. 화면 코드는 고치지 않아도 되고, `docs/architecture.md`의 노드 종류 표에 행을 더합니다. 같은 표의 `dailyNote` 설명에도 Obsidian 노트를 더합니다.
- 노트 때문에 처음 만들어지는 Jira 티켓 노드와 그 티켓의 작업 단위는 vault의 프로필과 무관하게 회사 프로필입니다. Notion 페이지와 배정 티켓이 만드는 티켓과 같습니다. 이미 있는 티켓 노드와 작업 단위의 프로필은 바꾸지 않습니다. 개인 vault의 노트도 노트 노드 자체는 개인 프로필로 남습니다.
- 노트의 이름은 확장자를 뺀 파일 이름입니다.
- 노트의 `url`은 `obsidian://open?path=<파일의 절대 경로>`입니다. [Obsidian URI 문서](https://help.obsidian.md/uri)의 `open` 형식이고, 값은 URI 인코딩합니다. 이 형식에서는 Obsidian이 그 경로를 포함하는 vault를 찾아 열므로, 설정의 `name`이 Obsidian의 vault 이름과 달라도 됩니다.
- 화면의 상세 패널은 지금 `http://`와 `https://` 주소만 링크로 만듭니다(`web/src/detail.ts`). `obsidian://open?`으로 시작하는 주소도 링크로 만들도록 고칩니다. 허용하는 형식은 이 세 가지뿐이고, 판정은 `web/src/link.ts`가 합니다.
- `http(s)` 링크는 주소마다 탭 하나를 열어 두고 다시 누르면 그 탭을 앞으로 가져옵니다(`openOnce`). `obsidian://` 링크에는 이 방식을 쓰지 않고 브라우저의 기본 동작에 맡깁니다. 탭을 열면 빈 탭만 남고, 다시 눌러도 그 빈 탭만 앞으로 올 뿐 노트가 열리지 않기 때문입니다.
- 노트가 만든 PR 노드의 이름은 `<저장소> #<번호>`입니다. PR의 제목이나 상태는 조회하지 않습니다.

### 처리 순서와 작업 단위

- Obsidian 노트는 `build_graph()`에서 "보낸 리뷰" 처리 다음에 넣습니다. 세션, 리뷰 요청, 보낸 리뷰가 만든 PR 노드가 먼저 있게 하기 위해서입니다.
- PR 노드가 이미 있으면 노트는 연결만 더하고, 그 노드의 종류, 프로필, 상세 정보를 바꾸지 않습니다. 본문에 PR 주소를 적는 것만으로는 "보낸 리뷰"와 "리뷰 요청" 카드가 달라지지 않습니다.
- 리뷰 요청은 제목의 Jira 키가 가리키는 작업 단위가 있으면 그 단위로 들어간다는 기존 규칙이 있습니다(`docs/architecture.md`의 "작업 단위"). 노트 제목에 그 키가 있으면 작업 단위가 생기므로, 그 리뷰 요청은 낱개 카드에서 티켓의 카드로 옮겨 갑니다. Notion 페이지 제목이나 세션이 그 작업 단위를 만들 때와 같은 동작이고, 이 변경에서 바꾸지 않습니다.
- 노트는 설정에 적은 vault 순서대로, 한 vault 안에서는 경로의 사전 순서대로 처리합니다. 아래에서 "처음"은 이 순서를 뜻합니다.
- 노트의 작업 단위는 제목으로 정합니다. 제목에 Jira 키가 있으면 첫 키의 티켓(또는 에픽)의 작업 단위이고, 없으면 노트 자신이 작업 단위입니다. Notion 페이지의 제목 규칙과 같습니다.
- 본문의 키는 작업 단위를 정하지 않습니다. 회의록 본문에 적힌 동료의 티켓이 내 작업 단위와 칸반 카드가 되지 않게 하기 위해서입니다.
- 티켓 노드가 이미 있으면 노트는 연결만 더하고, 그 노드의 프로필, 상세 정보, 이미 정해진 작업 단위를 바꾸지 않습니다. 이 점은 Notion 처리와 다릅니다(Notion은 제목에 나온 티켓의 작업 단위를 덮어씁니다).
- 예외가 하나 있습니다. 제목의 키가 가리키는 티켓 노드에 작업 단위가 아직 없으면(리뷰 요청 제목에서 만들어진 티켓) 노트의 작업 단위를 채웁니다. 채우지 않으면 `jira:<키>` 작업 단위는 생기는데 정작 그 티켓 노드는 "공통"에 남습니다. 본문의 키에는 이 예외를 적용하지 않습니다.
- 앞서 처리한 노트가 본문에서 언급해 만든 티켓(`mention`)도 같습니다. 뒤의 노트가 그 키를 제목에 가지면 `mention` 표시를 지우고 티켓 자신의 작업 단위로 옮깁니다. 노트를 처리하는 순서와 무관하게 결과가 같아야 하기 때문입니다.
- `mention` 티켓은 회사 프로필이므로, 개인 vault의 노트가 언급한 티켓은 화면의 개인 탭에서는 보이지 않고 전체나 회사 탭에서 보입니다.
- 제목의 키 때문에 처음 만들어지는 티켓 노드는 그 노트의 작업 단위에 넣습니다. 첫 키라면 그 티켓 자신의 작업 단위입니다.
- 본문의 키 때문에 처음 만들어지는 티켓 노드는 그 노트의 작업 단위에 넣고 `detail.mention`을 `true`로 표시합니다. 작업 단위가 없는 노드("공통")는 화면에 그리지 않으므로(`web/src/state.ts`의 `shown()`), 넣지 않으면 조회만 하고 보이지 않습니다.
- 칸반은 `mention` 표시가 있는 티켓을 그 작업 단위의 티켓으로 세지 않습니다(`board.py`). 세면 그 티켓의 Jira 상태가 노트 카드의 칸과 꼬리표를 정해서, 동료 티켓이 내 카드를 움직입니다.
- 태그 노드와 노트가 만든 PR 노드는 그것을 처음 연결한 노트의 작업 단위에 넣습니다.
- 세션 로그를 쓰는 동안에는 노트가 활동의 출처가 되지 않습니다. Notion, 커밋, 티켓과 같습니다(`graph.py`의 `touch()`).
- 노트는 Notion 페이지처럼 최근 활동 목록(`activity[]`)에도 한 줄씩 들어갑니다. `kind`는 `obsidian`이고 `text`는 노트 제목입니다. 활동 목록에 드는 기간은 다른 출처와 같습니다(`ACTIVITY_SEC`).

## 치르는 비용

- **파일 수정 시각에 의존합니다.** 동기화 도구나 일괄 편집이 수정 시각을 바꾸면 내가 고치지 않은 노트도 잡힙니다. Obsidian은 누가 고쳤는지 기록하지 않으므로 Notion의 `notion_user_id` 같은 선별 방법이 없습니다.
- **256KB 뒤의 내용은 읽지 않습니다.** 그보다 큰 노트에서는 잘린 뒤에 있는 링크, 태그, Jira 키, PR 주소가 빠집니다. 화면에는 빠졌다는 표시가 없습니다.
- **수정 시각이 미래인 파일은 그 시각이 될 때까지 계속 "방금 고친 노트"입니다.** 훑을 때마다 지금 고친 것으로 보므로 100개 안에 항상 들고, 가장 밝고, 활동 목록 맨 위에 옵니다. 시계가 틀린 기기에서 동기화된 파일에서 생길 수 있습니다. 빼 버리면 노트가 이유 없이 사라지므로 보이게 두었습니다.
- **100개를 넘는 노트는 구간 안에 있어도 빠집니다.** 빠진 노트는 노드가 되지 않으므로, 그 노트를 가리키는 링크와 그 노트만 가진 태그도 연결되지 않습니다. 화면에는 빠졌다는 표시가 없습니다.
- **늦게 보입니다.** 노트를 고친 뒤 화면에 보이기까지 훑는 간격 30초에 한 번 훑는 시간이 더해집니다. 훑는 시간은 vault 크기에 따라 달라지며 재지 않았으므로 상한을 말할 수 없습니다.
- **표시 이름에 `[`가 있는 링크는 읽지 않습니다.** `[[노트|참고 [1]]]` 같은 경우입니다. 닫히지 않은 `[[`가 많은 줄에서 찾는 시간이 길어지지 않도록 링크 안의 `[`를 허용하지 않기 때문입니다.
- **링크는 파일 이름으로만 찾습니다.** 같은 이름의 노트가 여러 폴더에 있으면 그래프에 있는 그 이름의 노트 모두와 연결합니다. Obsidian이 경로로 구분하는 경우까지 따라가지 않습니다.
- **머리말의 `tags:`는 흔한 세 가지 형태만 읽습니다.** `tags: [a, b]`, `tags: a, b`, 그리고 줄마다 `- a`로 쓰는 목록입니다. 표준 라이브러리에 YAML 해석기가 없기 때문입니다.
- **노트의 Jira 키가 조회 대상 100개를 함께 씁니다.** 노트에 티켓 번호가 많으면 조회 대상이 먼저 차서, 그 뒤에 처음 나온 티켓은 서버를 다시 시작할 때까지 요약과 상태가 조회되지 않고 키로만 보입니다. 세션이나 커밋에서 나온, 나에게 배정되지 않은 티켓이 여기에 해당합니다. 나에게 배정된 티켓은 `search_mine`이 조회 대상과 따로 받아 오므로 영향을 받지 않습니다. 어느 출처의 키가 먼저 들어가는지는 보장하지 않습니다.

## 남는 위험

- **노트마다 칸반 카드가 생깁니다.** 제목에 Jira 키가 없는 노트는 자신이 작업 단위가 되고, 작업 단위마다 카드가 하나 생깁니다. 일주일에 노트를 많이 고치면 카드가 그만큼 늘어납니다. Notion 페이지도 같은 방식이며, 이 변경에서 바꾸지 않습니다.
- **제목에 적은 티켓은 내 작업 단위가 됩니다.** 파일 이름에 동료의 티켓 번호를 넣으면 그 티켓이 내 작업 단위와 칸반 카드로 생기고, 티켓이 진행 중이면 "진행 중" 칸에 놓입니다. Notion 페이지 제목과 같은 동작입니다.
- **본문을 읽고, 일부가 그래프와 밖으로 나갑니다.** 본문 문장은 저장하지 않습니다. 그래프에는 vault 이름과 vault 기준 경로(노드 id), 파일의 절대 경로(`url`), 제목(노드 이름과 활동 목록), 태그, 뽑은 Jira 키와 PR 주소가 들어갑니다. 이 정보가 나가는 경로는 다음과 같습니다.
  - `GET /graph.json`: 접근 토큰을 가진 사람이 봅니다.
  - MCP 도구 `thync_now`(`thync/mcp.py`): 집중 중이거나 진행 중인 노드의 이름, 작업 단위, `url`을 연결된 에이전트에게 토큰 없이 돌려줍니다. 세션 로그를 쓰지 않는 설정에서는 노트도 집중 노드가 될 수 있습니다.
  - 세션 시작 hook(`thync/hook.py`): `GET /graph.json`을 읽어 `thync_now`와 같은 요약(이름, 작업 단위, `url`)을 새 Claude Code 세션의 문맥에 넣습니다.
  - Jira Cloud: 제목과 본문의 Jira 키를 조회합니다(위 "본문의 Jira 키와 Jira 조회").
  
  `docs/security.md`에 적습니다.
- **함께 고칠 문서.** `docs/configuration.md`(`sources`의 기본값 설명, 설정 키 표, "수집 주기와 범위" 표), `docs/architecture.md`(데이터 흐름, 노드 종류 표, `activity[].kind` 목록), `docs/security.md`, `README.md`, `config.example.json`입니다. 고치지 않으면 `sources` 기본값을 "다섯 가지"라고 한 설명이 코드와 어긋납니다.
- **큰 vault의 탐색 시간.** 한 번 훑을 때마다 vault 전체의 파일 정보를 읽고, 마치면 30초 뒤에 다시 훑습니다. 본문은 최대 100개만 읽습니다. 노트가 수만 개인 vault에서 걸리는 시간은 재지 않았습니다. 서버에서는 배경 스레드가 훑으므로 화면 요청은 기다리지 않습니다. MCP 서버에는 배경 스레드가 없어서, `thync_now` 호출은 보관된 결과가 30초보다 오래되었으면 vault를 다 훑을 때까지 기다립니다.
