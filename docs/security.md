# 데이터와 보안

[문서 목차](README.md) · [프로젝트 소개](../README.md)

thync는 수집한 작업 정보를 로컬 화면에 제공합니다. 외부 서비스 조회와 PR 위임 과정에서는 해당 서비스와 통신합니다. 아래에서 저장 위치, 접근 방식, 서비스별 쓰기 범위를 확인할 수 있습니다.

## 접근 토큰과 저장 위치

서버는 `THYNC_HOME`(기본 `~/.thync`) 디렉터리를 `0700`, 접근 토큰 파일을 `0600`으로 설정합니다. Jira·Notion 토큰 파일도 [설정 안내](configuration.md#jira와-notion-연결)에 따라 `0600`으로 만듭니다. 개인 경로·회사 설정·토큰·수집 데이터는 저장소 밖에 둡니다.

서버는 `127.0.0.1`에서 실행합니다. 정적 화면은 토큰 없이 제공하지만, `/graph.json`과 쓰기 요청은 `X-Thync-Token` 헤더가 서버 토큰과 일치해야 허용합니다. 같은 머신의 다른 사용자도 로컬 주소에 접속할 수 있고, [Tailscale로 접속](getting-started.md#tailscale로-접속하기)할 때는 tailnet 접근 규칙(ACL)이 허용한 모든 기기가 접속할 수 있으므로 토큰을 함께 확인합니다. 요청의 `Host`가 로컬 호스트 이름(`127.0.0.1`, `localhost`, `::1`)이나 `*.ts.net`인지도 검사해, 임의의 도메인을 이용한 DNS 리바인딩을 막습니다. `*.ts.net`은 Tailscale로 접속할 때의 주소입니다. 이 도메인의 공개 DNS는 Tailscale이 응답하지만, 신뢰할 수 없는 Wi-Fi처럼 DNS 응답을 조작할 수 있는 네트워크에서는 이 이름으로도 리바인딩이 가능하므로, 이때 데이터와 쓰기 요청을 막는 것은 접근 토큰과 아래 `tailscale_users`의 조건입니다.

`tailscale_users`에 적은 Tailscale 로그인 이름은 토큰 대신 쓸 수 있고, 토큰과 같은 권한을 받습니다. `tailscale serve --bg <포트>`(HTTPS 프록시)는 요청에 접속한 사람의 로그인 이름을 `Tailscale-User-Login` 헤더로 붙이고, 클라이언트가 직접 보낸 같은 이름의 헤더는 지웁니다. Funnel로 들어온 요청과 태그가 붙은 기기의 요청에는 이 헤더가 붙지 않습니다. 서버는 아래 세 조건을 모두 만족할 때만 이 이름을 믿습니다.

- `Host`가 이 컴퓨터의 MagicDNS 이름과 같습니다. 서버가 시작할 때 `tailscale status`로 읽고, 그때 읽지 못했으면 요청이 올 때 1분에 한 번 다시 읽습니다. Tailscale이 켜져 있고 Tailscale DNS 설정(`--accept-dns`)을 쓰는 기기에서는 MagicDNS가 이 이름에 직접 응답하므로, DNS 응답을 조작할 수 있는 네트워크에서도 이 이름을 `127.0.0.1`로 바꾸는 DNS 리바인딩이 통하지 않습니다.
- 요청에 `X-Thync-Token` 헤더가 있습니다. 값은 비어 있어도 됩니다. thync 화면은 모든 요청에 이 헤더를 붙입니다. 다른 사이트의 페이지는 CORS 사전 요청(preflight)을 거쳐야 이 헤더를 보낼 수 있는데, 서버는 사전 요청을 허용하지 않습니다. 그래서 다른 사이트가 내 브라우저를 통해 요청을 보내는 CSRF(사이트 간 요청 위조)를 막습니다.
- 헤더의 로그인 이름이 목록에 있습니다.

이 헤더는 서버가 직접 확인할 수 없으므로, 아래 경우에는 목록의 사용자로 행세할 수 있습니다.

- 이 컴퓨터의 다른 프로세스: `127.0.0.1`로 직접 세 조건을 모두 갖춘 요청을 보낼 수 있습니다. 다른 사용자가 있는 컴퓨터에서는 `tailscale_users`를 비워 둡니다.
- `tailscale serve --tcp`나 `--tls-terminated-tcp`로 연 경우: HTTP 헤더를 지우지 않으므로, tailnet 접근 규칙(ACL)이 허용한 모든 기기가 헤더를 보낼 수 있습니다. `tailscale_users`를 쓸 때는 `tailscale serve --bg <포트>`로만 엽니다.
- 이 서버로 SSH 포트 포워딩을 연 컴퓨터: 허브의 `remotes` 연결과 손으로 연 `ssh -L` 모두, 그 컴퓨터의 프로세스가 포워딩된 포트로 같은 요청을 보낼 수 있습니다. 그 컴퓨터에서 Tailscale이 꺼져 있거나 Tailscale DNS 설정을 쓰지 않는 상태로 DNS 응답을 조작할 수 있는 네트워크에 연결되어 있다면, 그 컴퓨터의 브라우저에서 리바인딩도 가능합니다. 그 컴퓨터도 혼자 쓰고, Tailscale을 켜 두고 Tailscale DNS 설정을 켜 둡니다.

토큰이 없거나 틀리면 화면 위쪽에 토큰 입력 칸이 나옵니다. 브라우저는 입력 칸이나 최초 접속 주소의 `#t=`에서 받은 토큰을 `localStorage`에 저장하고, `#t=`는 주소창에서 지웁니다. 토큰은 URL 쿼리에 넣지 않습니다. 원격 서버를 사용할 때는 [SSH 포트 포워딩](getting-started.md#원격-서버에서-실행하기)이나 [Tailscale](getting-started.md#tailscale로-접속하기)로 연결합니다.

## 데이터 흐름과 쓰기 범위

| 대상 | 읽거나 처리하는 내용 | 쓰기 범위 |
| --- | --- | --- |
| 로컬 파일 | 설정, 카드, 이름 변경, 위임 기록, 선택적으로 Claude Code·Codex 세션 로그 | 카드 편집·이름 변경·위임 상태 등을 `THYNC_HOME` 또는 설정한 카드 폴더에 저장합니다 |
| GitHub | `gh`로 내 커밋·리뷰 요청·내 PR을 조회합니다 | 사용자가 맡긴 PR에서만 씁니다. 다른 사람의 PR에는 리뷰와 승인을, 내 PR에는 수정·push·답글·병합 등 [허용 동작](handoff.md#작업과-허용-동작)을 Concord 작업이 실행 계정으로 씁니다 |
| Jira | 설정한 API로 티켓을 조회합니다 | 쓰지 않습니다 |
| Notion | 설정한 API로 페이지를 조회합니다 | 쓰지 않습니다 |
| Obsidian | `obsidian_vaults`에 적은 폴더의 `.md` 파일을 이 컴퓨터에서 읽습니다. 본문에서는 노트 링크, 태그, Jira 키, GitHub PR 주소만 뽑고 문장은 저장하지 않습니다. `obsidian_board`에 적은 Kanban 보드 파일 하나는 예외로, 카드의 글을 읽어 칸반에 보여 줍니다 | 쓰지 않습니다. 보드 카드는 thync에서 옮기거나 고칠 수 없습니다 |
| Claude CLI | PR 위임 시 PR 내용과 로컬 저장소 내용을 처리합니다 | 외부 통신과 데이터 처리는 해당 CLI 설정과 서비스 정책을 따릅니다 |

Jira·Notion 요청은 리다이렉트를 따라가지 않아 토큰이 다른 호스트로 전달되는 것을 차단합니다. 출처별 수집 범위와 주기는 [설정 안내](configuration.md#수집-주기와-범위)에 설명합니다.

Obsidian 노트에서 그래프에 들어가는 정보는 vault 이름, vault 기준 경로, 파일의 절대 경로(노트를 여는 `obsidian://` 주소), 제목, 두 노트 이상이 함께 가진 태그, 본문에서 뽑은 Jira 키와 PR 주소입니다. 이 정보는 다음 경로로 나갑니다.

- `GET /graph.json`: 접근 토큰을 가진 사람이 봅니다.
- MCP 도구 `thync_now`와 세션 시작 hook: 집중 중이거나 진행 중인 노드의 이름, 작업 단위, 주소를 연결된 에이전트와 새 Claude Code 세션에 전달합니다.
- Jira: 노트 제목과 본문에 적힌 Jira 키를 설정한 Jira 서버에 조회합니다. Jira 토큰이 없으면 조회하지 않습니다.

`obsidian_board`를 설정하면 그 보드의 카드 글(제목 200자, 메모 4,000자까지, 200장까지), 카드가 속한 칸의 이름(100자까지)과 보드 파일의 절대 경로가 `GET /graph.json`의 `board`로 나갑니다. 접근 토큰을 가진 사람이 봅니다. MCP 도구 `thync_now`와 세션 시작 hook의 요약에는 보드 카드의 글이 들어가지 않습니다. 공유하거나 동기화하는 vault의 보드에는 다른 사람이 쓴 글이 있을 수 있으며, 화면은 카드 글을 글자로만 표시합니다.

vault 밖의 파일을 읽지 않도록 심볼릭 링크는 따라가지 않습니다. 보드 파일도 보통 파일일 때만 읽습니다.

## PR 위임의 권한 범위

두 작업 모두 PR 저장소의 로컬 클론에서 tmux 안의 대화형 Claude Code 세션으로 돌고, `--permission-mode auto`를 씁니다. 세션은 클론을 맡은 mien 프로필로 실행하며(`mien exec`), mien이 없으면 서버 프로세스의 `gh` 계정으로 실행합니다.

| 대상 | 작업 | 결과 |
| --- | --- | --- |
| 다른 사람의 PR | `concord:review-until-approve` | Concord가 PR 헤드를 임시 폴더에 받아 리뷰하고, 실행 계정으로 리뷰와 승인을 게시합니다 |
| 내 PR | `concord:pr-to-merge` (`OWNER/REPO#N` 하나) | 리뷰 지적을 고쳐 push하고 답글을 달며, 조건을 채우면 그 PR을 병합합니다 |

- PR 본문, 코드, 리뷰어 코멘트는 외부에서 작성한 입력입니다. 숨은 지시가 리뷰 문구와 승인 판단을 왜곡할 수 있습니다.
- 다른 사람의 PR을 리뷰하는 Claude 리뷰어는 격리되지 않아 홈 디렉터리의 `gh`·`ssh`·클라우드 자격 증명을 읽을 수 있습니다. 그래서 사용자가 세션에서 직접 신뢰를 써야 실행되고, thync는 이 선언을 대신 쓰지 않습니다([신뢰 선언](handoff.md#다른-사람의-pr-신뢰-선언)).
- 내 PR의 세션도 리뷰어와 자동 리뷰어가 쓴 코멘트를 읽고, auto 권한과 push·병합 허락으로 움직입니다.
- `~/.thync`·`~/.ssh`·`~/.claude/settings.json`에 대한 `Read(...)` 거부는 Read 도구에만 적용됩니다. 셸 명령으로 읽는 것은 막지 않으며, 전체 프로세스를 격리하는 운영체제 샌드박스를 뜻하지 않습니다. 두 세션 모두 셸로 `mien exec`가 넣은 `GH_TOKEN` 같은 환경 변수와 `~/.thync/token`을 읽을 수 있습니다. 이 토큰은 thync의 모든 쓰기 요청을 허락하므로, 숨은 지시에 속은 세션은 같은 머신에서 다른 PR 위임을 시작하거나, 다른 세션의 선택 질문에 대신 답하거나, 카드를 바꿀 수 있습니다. 이때도 실행하는 머신의 작성자·계정 확인은 그대로 적용됩니다.
- 확인 창에 보인 계정·프로필·작업이 시작할 때 다르면 시작하지 않습니다. PR 작성자는 실행하는 머신이 그 계정으로 다시 확인하며, 화면이나 허브가 보낸 노드의 역할만 믿지 않습니다.

## 세션 로그 연동의 한계

Claude Code와 Codex 세션 로그는 공개된 형식이 아니므로 버전에 따라 읽기에 실패할 수 있습니다. 세션 로그를 사용하지 않으려면 `sources`에서 `claude_code`와 `codex`를 모두 제외합니다. `claude_code`를 제외하면 PR 위임 기능도 비활성화됩니다.
